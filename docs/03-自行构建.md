# 自行构建指南

> 本发布里的构建材料是**自包含**的，两条链都给了：
> **A) 只改 DTB → 重建 boot**（最常见，分钟级）
> **B) 从零做一套 rootfs**（小时级，需要 Linux 构建机）
>
> 建议先读完 [`../README.md`](../README.md) 的「引导链」一节，理解 DTB 为什么这么关键。

---

## 〇、先选一条链

| 你的目标 | 走哪条 | 材料 | 耗时 |
|---|---|---|---|
| 调 WiFi / GPU 频率 / 电源域 / 加个设备节点 | **链 A** | `boot-build/` + `dtb/` | 1~5 分钟 |
| 换个内核参数、改 cmdline、换内核 | **链 A**（+ `rebuild-boot.py`） | 同上 | 1~10 分钟 |
| 改系统服务、加软件、改包列表、换发行版 | **链 B** | `rootfs-build/` | 首次 1~2 小时 |
| 只是想用，不想构建 | 都不用 | 直接用 `boot/` + `rootfs/` 成品 | 20 分钟（刷机） |

---

## 一、环境准备

| 项 | 要求 |
|---|---|
| 构建主机 | **Linux**（Ubuntu 22.04/24.04 推荐），Windows 上用 **WSL2** |
| 依赖 | `dtc` `fdtget`（`device-tree-compiler`）、`python3`、`patch`、`sha256sum` |
| 磁盘 | 链 A 几乎不占；**链 B 需要 ≥ 50 GB 可用** |
| 内存 | 链 B 建议 ≥ 8 GB |
| 网络 | 链 B 要能访问 github.com / kernel.org / debian 源 |

```bash
sudo apt update
sudo apt install -y device-tree-compiler python3 patch
dtc --version      # 1.6.x 以上都可以
```

> ⚠️ **在 WSL 里构建时，源码不要放 `/mnt/c/` 或 `/mnt/e/` 下**（跨文件系统极慢，且 chroot 会出问题）。
> 放到 WSL 自己的文件系统里，比如 `~/build`。

## 二、链 A：只改 DTB → 重建 boot

### 步骤

```bash
cd <本发布根目录>

# ① 改设备树（源文件在这里）
vi dtb/slim-ovf-wifi6-gpu-oc-final.dts

# ② 一条命令重建（自带前置检查 + DTB 校验 + 重打包 + sha256 对比）
bash boot-build/build-boot.sh
# 产物：boot-build/out/boot-rebuilt.img
```

脚本会强制校验三件事（缺一个就中止，因为**任何一项不合格都会导致机器秒进 fastboot**）：

| 校验 | 期望 |
|---|---|
| `dtc` 是否带 `-@`（生成 `__symbols__`） | `__symbols__.arch_timer = /timer` |
| `/abl_ovf` 锚点树 | **≥ 152 个节点** |
| `model` | umi 的机型字符串 |

### ✅ 这条链是可复现的（已实测）

不改任何东西直接重跑，产物与随包成品**逐字节一致**：

```
DTB  : b0e48ef96880567160182be4d31dc5721fa33ce3b3551909388b8e50612a99c2  ✓
BOOT : a7e4d341e35a663683bf41a8fe99d472bc6b8568aa1b54b05901dc7e9f2d842a  ✓
```

如果你**改了** DTS，sha256 自然会变——发版时记得同步 `SHA256SUMS.txt`。

### 从上游 Armbian 基线开始（更"从零"）

上游的 boot 镜像是 **header v0**（DTB 追加在 kernel.gz 之后，没有独立 dtb 段），
本项目的 `replace-dtb.py` 需要 **v2**。所以要先转：

```bash
python3 boot-build/tools/rebuild-boot.py --src <Armbian基线boot.img> --out /tmp/v2.img \
        --slim --disable-dsp --ramoops
bash boot-build/build-boot.sh /tmp/v2.img out/boot-from-scratch.img
```

细节（含 `dts.patch` 改了什么、`/abl_ovf` 怎么重新生成）见 **[`../boot-build/BUILD.md`](../boot-build/BUILD.md)**。

## 三、链 B：从零构建 rootfs

`rootfs-build/` 就是 **Armbian `build` 框架的 umi 移植包**：
板级配置 + 3 个板级 DTS + 内核补丁依赖校验 + `overlay/`（进 rootfs 的服务与脚本）+ 构建扩展。

### 步骤

```bash
# ① 取 Armbian 构建框架
cd ~
git clone --depth 1 https://github.com/armbian/build.git
cd build
grep -A2 'current)' config/sources/families/sm8250.conf    # 确认内核主版本（本项目按 6.18 验证）

# ② 应用 umi 移植（把本包的 rootfs-build/ 拷到构建机）
~/rootfs-build/apply-umi-port.sh ~/build
#    它做四件事：装板级配置、装 3 个 DTS 到 patch/kernel/archive/sm8250-6.18/dt/、
#    装 BSP 包、校验依赖的充电补丁是否齐全

# ③ 构建
./compile.sh build \
    BOARD=xiaomi-umi \
    BRANCH=current \
    RELEASE=trixie \
    BUILD_MINIMAL=yes \
    BUILD_DESKTOP=no \
    KERNEL_CONFIGURE=no \
    ENABLE_EXTENSIONS="docker-ce umi-usb-host umi-firstboot umi-kernel-tweaks" \
    EXPERT=yes
```

产物在 `output/images/`：

```
Armbian_<版本>_Xiaomi-umi_trixie_current_6.18.x_minimal.rootfs.img              # 刷 rootfs（userdata）
Armbian_<版本>_Xiaomi-umi_trixie_current_6.18.x_minimal.boot_sm8250-xiaomi-umi-csot.img   # 刷 boot
```

> **面板一定要选对**：`csot`（华星光电）还是 `sms`，决定用哪个 DTS / boot 镜像。
> 查法见 [`01-快速开始.md`](01-快速开始.md) §〇。

### 刷机

```bash
fastboot flash boot   Armbian_..._boot_sm8250-xiaomi-umi-csot.img
fastboot flash userdata Armbian_..._rootfs.img      # 不要安卓 → 直接给 userdata
# ★ 别忘了 dtbo 必须是原厂的
```

首次开机后**务必整盘扩容**（rootfs 镜像是按最小尺寸生成的）：

```bash
resize2fs $(findmnt -no SOURCE /)
df -h /
```

更详细的参数说明、扩展作用、开箱默认值见 **[`../rootfs-build/BUILD.md`](../rootfs-build/BUILD.md)**。

### ⚠️ 这份 rootfs 构建材料的时效说明（重要，别踩坑）

`rootfs-build/` 是 **9 月中旬那一版**的移植框架，它自带的服务是：

```
overlay/usr/local/bin/battery-charge-limit   （充电区间）
overlay/usr/local/bin/panel-hold / panel-power（息屏）
overlay/root/wifi-connect.sh                  （配 WiFi）
overlay/etc/systemd/system/{battery-charge-limit,panel-off}.service
```

**而随包镜像（`rootfs/`）里还多跑着一批 9-27 前后加的服务**，它们目前**没有**全部回填到
`rootfs-build/overlay/`，请自行合并：

| 服务 | 作用 | 从哪拿 |
|---|---|---|
| `umi-venus-enable` | MMCX 上电 + 加载 Venus（视频硬编解） | 镜像内 `/usr/local/sbin/` + `/etc/systemd/system/` |
| `umi-gpu-maxfreq` | GPU 频率上限 | `rootfs-config/`（本包已存快照） |
| `usb-gadget-umi` | USB 网卡 + 串口 | 镜像内 |
| `umi-bcb-early` / `umi-return-recovery` | 保命回 TWRP | 镜像内 |
| `boot-collect` | 开机采集诊断快照 | 镜像内 |

**合并方式**（Armbian overlay 的约定就是照目录结构覆盖）：

```bash
cp <你的脚本>   rootfs-build/userpatches/overlay/usr/local/sbin/
cp <你的 unit>  rootfs-build/userpatches/overlay/etc/systemd/system/
```

或者更直接：**在设备上把现有服务导出来**（`tar czf - /usr/local/{bin,sbin} /etc/systemd/system`），
作为你自己 overlay 的起点。

## 四、常见改动怎么做（速查）

| 想改什么 | 改哪里 | 需要重刷 |
|---|---|---|
| WiFi 的 PCIe/电源域配置、加设备节点 | `dtb/slim-….dts` → 链 A | boot |
| GPU 频率档位（新增/删档、超频） | DTS 里 `&gpu { opp-table { … } }` → 链 A | boot（**只需一次**，之后用 sysfs 调） |
| Venus OPP 表 | DTS 里 `video-codec@aa00000` 的 `opp-table` → 链 A | boot |
| 内核 cmdline（如 `consoleblank`） | `rebuild-boot.py --cmdline "..."` | boot |
| CPU 调频策略 | 设备上 `/etc/default/cpupower` | 不用刷 |
| 充电区间 | 设备上 `/etc/default/battery-charge-limit` | 不用刷 |
| GPU 频率上限 | 设备上 `/etc/default/umi-gpu-maxfreq` | 不用刷 |
| 加一个开机服务 | `rootfs-build/userpatches/overlay/…` → 链 B | rootfs |
| 换发行版（如 Ubuntu 24.04） | 链 B 的 `RELEASE=noble` | rootfs |
| 换内核版本 | 链 B 的 `BRANCH=edge`；或用 `rebuild-boot.py` 换 Image | boot |

## 五、构建后的自检清单（别跳过）

```bash
# 1) 镜像校验
sha256sum boot-build/out/boot-rebuilt.img
sha256sum -c SHA256SUMS.txt            # 若你改了文件，先重算清单（见下）

# 2) DTB 结构自检（不刷机也能查）
fdtget boot-build/out/rebuilt.dtb /__symbols__ arch_timer      # 期望 /timer
fdtget -l boot-build/out/rebuilt.dtb /abl_ovf | wc -l          # 期望 >= 152
fdtget boot-build/out/rebuilt.dtb / model

# 3) 刷机后（见 01-快速开始.md §四 的验收清单）
systemctl --failed
ls /dev/dri /dev/video*
```

**重算校验清单**（改了发布目录里任何文件之后）：

```bash
cd <本发布根目录>
find . -type f ! -name SHA256SUMS.txt -printf "%p\n" | sort \
  | xargs sha256sum | sed 's|  \./| *./|' > SHA256SUMS.txt
sha256sum -c SHA256SUMS.txt
```

## 六、三个最容易踩的坑

1. **忘了 `dtc -@`** → DTB 没有 `__symbols__` → ABL 的 overlay 应用失败 → **设备秒进 fastboot**。
   （`build-boot.sh` 会自动拦住这种情况。）
2. **行尾写成 CRLF** → 在 Windows 用文本模式（`open(f,"w")` 之类）写 `.dts` 会把 LF 变 CRLF，
   于是 `diff` / `patch` 全文件失配。**写 DTS 一律用二进制模式或写完做 LF 归一化**
   （DTB 本身不受影响，因为它由 dtc 编译）。
3. **动 `dtbo` 分区** → 必须保持原厂。它提供 ABL 需要的板级 overlay，换掉或留空都开不了机。
