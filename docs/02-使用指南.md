## 〇、账号与密码（先看这个）

镜像里的账号状态（已逐项核对 `/etc/passwd` / `/etc/shadow` / `/etc/group`）：

| 账号 | 密码 | 能否登录 | 权限 / 说明 |
|---|---|---|---|
| **`root`** | **`umi10linux`** | ✅ 串口（**免密**）/ SSH / 本地 | uid 0；`/etc/ssh/sshd_config.d/99-umi.conf` 里 `PermitRootLogin yes` + `PasswordAuthentication yes` |
| **`armbian`** | **`armbian`** | ✅ SSH / 本地 | uid 1000，家目录 `/home/armbian`；**在 `sudo`、`docker`、`adm`、`disk`、`tty`、`render` 等组** → `sudo` 一下就是 root，**风险与 root 同级** |
| `www` | — | ❌ 已锁定（`!`） | 宝塔面板残留账号，无法登录；不需要就 `userdel www` |
| `sync` | — | ❌ 已锁定（`*`） | 系统账号，shell 为 `/bin/sync` |
| 其余 21 个系统账号 | — | ❌ 全部锁定 | `daemon`/`bin`/`sys`/`sshd`/`systemd-*`/`_apt`/`nobody` 等 |

**用串口登录不需要密码**（`agetty --autologin root`）；用 SSH 才需要密码。

**上线前请务必做**：

```bash
passwd                      # 改 root 密码（默认值是公开文档里的）
passwd -l armbian           # 锁掉 armbian（它在 sudo + docker 组，是第二把 root 钥匙）
# 更彻底：只留密钥登录
sed -i 's/^PasswordAuthentication yes/PasswordAuthentication no/' /etc/ssh/sshd_config.d/99-umi.conf
systemctl restart ssh
```

改完后查看账号状态：

```bash
passwd -S root              # P=有密码 / L=锁定 / NP=无密码
passwd -S armbian
awk -F: '$2 ~ /^\$/ {print $1" 有密码"}' /etc/shadow     # 列出所有有密码的账号
getent group sudo docker    # 看谁在这些特权组里
```

## 一、先搞清楚：这台机器有哪三条"进门"通道

| 通道 | 物理连接 | 地址 | 特点 |
|---|---|---|---|
| **① USB 串口** | 一根 USB 线插电脑 | Windows `COMx`；Linux `/dev/ttyACM0` | **免登录直接 root shell**。SSH/WiFi 全挂时靠它救砖 |
| **② USB 有线网卡** | 同一根 USB 线 | 设备 `172.16.42.1`，电脑自动拿 `172.16.42.2` | **Windows 免驱**，实测 426 Mbps。传文件、跑 Docker 都走它 |
| **③ WiFi** | 无线 | 路由器 DHCP 分配（如 `10.10.10.x`） | 摆脱线缆，配一次后开机自连 |

> **一根线同时提供 ① 和 ②**（设备侧是一个 USB composite gadget：`ncm.usb0` 网卡 + `acm.usb0` 串口）。

## 二、连串口（推荐第一个用它）

### Windows

1. 插 USB 线，等 10~20 秒；**设备管理器 → 端口 (COM 和 LPT)** 会出现一个 `USB 串行设备 (COMx)`，
   记下 `x`（本机是 `COM7`）。
2. 用任意串口工具连：**波特率 115200，8 数据位，无校验，1 停止位，无流控**。

```powershell
# PuTTY（图形）
putty.exe -serial COM7 -sercfg 115200,8,n,1,N
# 命令行（需装 plink）
plink.exe -serial COM7 -sercfg 115200,8,n,1,N
```

### Linux / macOS

```bash
ls /dev/ttyACM*            # 通常 /dev/ttyACM0
screen /dev/ttyACM0 115200
# 或
sudo picocom -b 115200 /dev/ttyACM0
sudo minicom -D /dev/ttyACM0 -b 115200
```

**退出**：`screen` 按 `Ctrl-A` 再按 `K`；`picocom` 按 `Ctrl-A Ctrl-X`。

### 你会看到什么

- 设备侧跑的是 `agetty --autologin root`，所以**打开串口就是 root shell**，不需要输密码。
- 设备端的设备名是 `/dev/ttyGS0`。

### 串口注意事项

- **串口默认 ASCII 编码**，中文会变 `?`（只影响注释显示）。经串口传脚本请用纯 ASCII。
- 日志会一直往串口刷；想看干净输出先 `dmesg -n 1` 或 `systemctl stop serial-getty@ttyGS0`（**别停**，那是你唯一的救命通道）。
- **短按电源键 = 干净关机**（`logind` 的 `HandlePowerKey=poweroff`），不是唤醒屏幕。

## 三、连 USB 网卡（SSH）

### Windows

插上 USB 线后，Windows 会自动加载自带的 `usbncm.inf` 驱动，网络连接里出现
**"UsbNcm Host Device"**（本机叫「以太网 3」），地址是 `172.16.42.2`。

```powershell
ping 172.16.42.1
ssh root@172.16.42.1
```

- 如果网卡没拿到 IP：给它手动配 `172.16.42.2 / 255.255.0.0` 即可（设备侧有 DHCP，但 Windows 偶尔不主动要）。
- 没装 OpenSSH 客户端：Windows 10/11 自带 `ssh`；或用 MobaXterm / PuTTY。

### 免密登录（可选）

把自己电脑的公钥放进设备的 `/root/.ssh/authorized_keys`：

```bash
ssh-copy-id root@172.16.42.1          # Linux/macOS
# 或从串口里贴： echo 'ssh-ed25519 AAAA... your@pc' >> /root/.ssh/authorized_keys
```

### 传文件

```bash
scp file.bin root@172.16.42.1:/root/          # 上传
scp -r root@172.16.42.1:/data/diag .          # 下载诊断快照
```

> 设备上还有个 **`umi-put`**（8080 端口 HTTP 文件推拉，**无鉴权**）。为安全起见本镜像
> **默认不自启**，需要时 `systemctl start umi-put`，用完记得 `stop`。

## 四、配 WiFi（QCA6390 / ath11k）

> **镜像里 DHCP 已经配好了**（`/etc/systemd/network/25-wlan.network`：`Type=wlan` → `DHCP=yes`，
> 并把主机名以 `umi10` 上报）→ **路由器上会看到一台叫 `umi10` 的设备**。
> 所以你要提供的**只有 SSID 和密码**，不需要自己配 IP。

### 方法 A：交互式脚本（推荐）

```bash
bash /root/wifi-connect.sh
```

流程：扫描 → 列出附近 WiFi（含信号强度、是否加密）→ 输入编号 → 输入密码 → 自动连接并等 IP。
支持输入 `m` 手动指定隐藏 SSID。

配置会**持久化**到这两个文件，重启后自动重连：

| 文件 | 内容 |
|---|---|
| `/etc/wpa_supplicant/wpa_supplicant-wlan0.conf` | WiFi 凭据（PSK 已哈希，**不是明文**） |
| `/etc/systemd/network/25-wlan0.network` | DHCP |

密码填错了？重跑一遍这个脚本即可（它会替换同名 network 块）。

### 方法 B：手动配置（不用脚本）

```bash
# 1) 生成 PSK 并写进 wpa_supplicant 配置
wpa_passphrase "你的SSID" "你的密码" >> /etc/wpa_supplicant/wpa_supplicant-wlan0.conf
chmod 600 /etc/wpa_supplicant/wpa_supplicant-wlan0.conf

# 2) 起两个服务
systemctl enable --now wpa_supplicant@wlan0
systemctl enable --now systemd-networkd

# 3) 确认
ip -br addr show wlan0
```

> ⚠️ 这套系统用的是 **systemd-networkd + wpa_supplicant**，**没有 NetworkManager、没有 `nmcli`**。
> 网上的 `nmcli` 教程在这台机器上不适用。

### 切换网络 / 删除已保存的 WiFi

```bash
wpa_cli -i wlan0 list_networks          # 列出已保存的网络（看 id）
wpa_cli -i wlan0 remove_network <id>    # 删掉某个
wpa_cli -i wlan0 save_config
# 或者直接编辑 /etc/wpa_supplicant/wpa_supplicant-wlan0.conf 后重启服务
```

### 固定 WiFi MAC（路由器做了 MAC 绑定时要）

```bash
printf '[Match]\nType=wlan\n\n[Link]\nMACAddress=xx:xx:xx:xx:xx:xx\n' \
  > /etc/systemd/network/10-wlan-mac.link
systemctl restart systemd-networkd
ip link show wlan0 | grep ether
```

### WiFi 排障

```bash
lspci -nn | grep 17cb                 # 期望看到 QCA6390 [17cb:1101]
dmesg | grep -i ath11k                # 期望 qca6390 hw2.0 / MSI vectors
ip -br link | grep wlan0              # wlan0 存在？
wpa_cli -i wlan0 status               # wpa_state 期望 COMPLETED
iw dev wlan0 link                     # 期望 Connected to ... SSID: ...
networkctl status wlan0
journalctl -u wpa_supplicant@wlan0 -n 50 --no-pager
journalctl -u systemd-networkd -n 50 --no-pager
rfkill list                           # 有没有被软/硬阻塞
```

> **正常但看着像报错的一条**：`dmesg` 里约 1.95 秒处的
> `qcom-pcie 1c00000.pcie: Phy link never came up` 是**无害**的 —— 控制器先探测，
> 芯片 7.7 秒才被 pwrseq 上电，链路随后自动建立。**判断看有没有 `01:00.0` 端点 / `wlan0`，别看这条。**

### 关于 WiFi 省电

- `iw dev wlan0 get power_save` → **off**（本项目选择关掉，换取稳定与低延迟）。
- 想开：`iw dev wlan0 set power_save on`（重启失效，要持久化得写 unit）。
- 硬件支持 WoWLAN（magic packet 唤醒等），但**默认未启用**，本方案也不需要。

## 五、设置充电上限（电池保护）

默认策略：**充到 70% 停充，掉到 65% 恢复**（长期把电量维持在 65~70%，明显减缓电池老化）。

### 改阈值

```bash
vi /etc/default/battery-charge-limit
#   UPPER=70      电量 ≥ 70% 停充
#   LOWER=65      电量 ≤ 65% 复充
#   INTERVAL=30   轮询间隔（秒），仅用户态兜底路径用

systemctl restart battery-charge-limit      # ★ 配置是启动时读入的，必须重启服务
```

### 看状态

```bash
cat /sys/class/power_supply/qcom-battery/capacity              # 电量 %
cat /sys/class/power_supply/pm8150b-charger/charging_enabled   # 1=允许充电 0=已停
journalctl -u battery-charge-limit -f                          # 直观看它的决策日志
```

日志长这样：

```
[charge-limit] 电池设备：/sys/class/power_supply/qcom-battery
[charge-limit] 使用用户态轮询：充电器 /sys/class/power_supply/pm8150b-charger 的 charging_enabled
[charge-limit] 电量 77% ≥ 70% → 已停止充电
```

### 想恢复"插上就充满"

```bash
systemctl disable --now battery-charge-limit
echo 1 > /sys/class/power_supply/pm8150b-charger/charging_enabled   # ★ 别忘了这句！
```

> ⚠️ **停掉服务时必须手动写回 `charging_enabled=1`**，否则会一直不充电。

### 两个要知道的坑

1. **不要用 `qcom-battery` 的 `current_now` / `status` 判断是否在充电** —— 本移植上不可信
   （实测边充边报 `Discharging`，数值前后差 200 倍）。
   **正确姿势**：看 `pm8150b-charger/current_now`（0 µA = 停充，≈250 mA = 在充）+ `capacity` 趋势。
2. **过冲最多 1%**：`capacity` 是 1% 步进 + 30 秒轮询，可能到 71% 才停，对电池保护无影响。

## 六、GPU（Adreno 650）

渲染节点：`/dev/dri/renderD128`（渲染）、`/dev/dri/card1`。

### 看/改频率

```bash
DEV=/sys/class/devfreq/3d00000.gpu
cat $DEV/available_frequencies     # 12 档：305/400/441.6/490/525/587/670/700/750/800/870/900 MHz
cat $DEV/cur_freq                  # 当前频率
cat $DEV/governor                  # simple_ondemand

echo 800000000 > $DEV/max_freq     # 设上限（调速器在此范围内自动升降）
echo 305000000 > $DEV/min_freq     # 设下限
echo 900000000 > $DEV/min_freq; echo 900000000 > $DEV/max_freq   # 钉死在某一档（压测用）
```

### 默认上限与持久化

镜像默认把上限锁在 **800 MHz**（`umi-gpu-maxfreq.service` 开机早期写入）：

```bash
vi /etc/default/umi-gpu-maxfreq     # GPU_MAX_FREQ=800000000
systemctl restart umi-gpu-maxfreq
```

- 想回**原厂保守值**：改成 `587000000`。
- 想上**实测极限**：改成 `900000000`（需要 NOM_L1 电压档，本项目已验证 60 秒长烤稳定）。

### ⚠️ 超频的风险

- 670 MHz 以上档位**超出芯片熔丝（speed-bin）验证范围**，属于超频。
- **本内核没有注册 GPU cooling device → 没有过热降频保护。** 长期满载请自行关注温度：
  ```bash
  cat /sys/class/thermal/thermal_zone*/temp
  ```
- 实测参考：8 进程满载 GPU 温度约 40~42 ℃；900 MHz 长烤约 57 ℃、245~279 fps。
- 想验证自己的超频是否真稳，**别用 `glClear`**（Adreno 是 TBDR，`glClear` 会被优化成"快清"，
  不反映真实负载）—— 要用带依赖链的重着色器负载 + 每帧 `glFinish` + 像素回读比对 + `dmesg` 查
  `gpu fault`/`hangcheck`。

### 自检 GPU 是否真的在工作

```bash
ls -l /dev/dri/                          # 期望 renderD128 + card1
cat /sys/kernel/debug/dri/*/gpu          # gpu-initialized: 1 / revision: 650（需 root）
glxinfo -B 2>/dev/null | grep -i renderer   # 期望 FD650，不是 llvmpipe
vulkaninfo --summary 2>/dev/null | head -30 # 期望 Turnip Adreno 650
```

> **开机时 `adreno ... error -22 initializing firmware ... a650_zap.mbn` + `GPU_SET Timeout`
> 是无害的**：驱动 probe 早于 rootfs 挂载，**首次有人打开渲染节点时会自动重试成功**。
> 这条报错每次开机都有，不是故障。

## 七、视频硬编解码（Venus）

设备节点：`/dev/video0`（解码）、`/dev/video1`（编码）。开机由 `umi-venus-enable.service` 自动准备好
（它会先把 MMCX 电源域拉起来，再加载 venus 三件套）。

```bash
v4l2-ctl --list-devices
ls /dev/video*
journalctl -u umi-venus-enable -n 20 --no-pager
```

### 硬解

```bash
# H.264
ffmpeg -hwaccel v4l2m2m -c:v h264_v4l2m2m -i in.mp4 -f null -
# HEVC / H.265
ffmpeg -hwaccel v4l2m2m -c:v hevc_v4l2m2m -i in.mp4 -f null -
```

### 硬编

```bash
ffmpeg -f lavfi -i testsrc2=size=1920x1080:rate=30 -t 10 \
       -pix_fmt nv12 -c:v h264_v4l2m2m -b:v 12M -y out.h264
```

> ★ **硬编必须 `-pix_fmt nv12`**，否则报 `Encoder requires nv12 pixel format`。

### 实测性能（对比软解，1080p 150 帧 CPU user time）

| 任务 | 软 | 硬 | 提升 |
|---|---|---|---|
| H.264 解码 | 0.80 s | **0.14 s** | 5.7× |
| H.265 解码 | 1.38 s | **0.10 s** | 13.7× |

### 并发与边界

- 实测 **8 路 1080p30 并发硬编全部通过**；4 路解码 + 4 路编码混合并发同样全绿。
- ⚠️ **多路编码时把输入高度对齐到 32 像素**（如 736p / 1088p）。
  720p 会因为 FFmpeg 7.x 上游 `v4l2_buffers.c` 的高度对齐读越界 Bug 而偶发崩溃。
- 硬件吞吐额定约 **500 MP/s**（≈ 4K@60）；12/16 路并发会被驱动拒绝（`session error: event id:1006`），
  这是硬件超额，不是配置问题。

## 八、显示与息屏

- **没有面板驱动**。开机时 ABL 会留下一个 framebuffer（能看到一点启动信息），
  随后 `panel-off.service` 通过 GPIO **给屏幕彻底断电** —— **屏幕全黑是正常且期望的状态**。
- 好处：AMOLED 黑屏 = 像素不发光，**防烧屏 + 省掉约 3 W 白耗电**。
- 兜底：内核 cmdline 里还有 `consoleblank=60`（60 秒无输出自动 blank）。

```bash
systemctl status panel-off                 # 看它对屏幕做了什么
cat /sys/class/graphics/fb0/blank          # 期望 4（已 blank）
ls /usr/local/bin/panel-* /usr/local/bin/panel-hold   # 相关小工具
```

> **别想在这台机器上跑桌面。** 它是无头服务器。

## 九、服务清单（这台机器"自带"了什么）

```bash
systemctl list-unit-files | grep -E 'umi|panel|battery|charge|cpupower'
systemctl --failed            # 期望：正常情况下没有失败项
```

| 服务 | 作用 | 关掉会怎样 |
|---|---|---|
| `usb-gadget-umi.service` | USB 复合设备：NCM 网卡 + ACM 串口 | **你会同时失去网卡和串口两个通道**（唯一"别乱停"的服务） |
| `wpa_supplicant@wlan0` + `systemd-networkd` | WiFi 连接 | 掉 WiFi（还有 USB 通道兜底） |
| `panel-off.service` | GPIO 给屏幕断电（真息屏） | 屏幕会一直亮着（烧屏 + 耗电） |
| `umi-venus-enable.service` | MMCX 上电 + 加载 Venus | `/dev/video*` 消失，硬编解不可用 |
| `umi-gpu-maxfreq.service` | 开机设定 GPU 频率上限 | 上限变成 DTB 里的最大值（可能冲到 900 且无过热保护） |
| `battery-charge-limit.service` | 充电区间滞回控制 | **会一直充到 100%**（且若当时正处于停充状态，会一直不充，见 §五） |
| `cpupower.service` | CPU 调频策略（默认 `performance`） | 回落到内核默认 `schedutil` |
| `umi-bcb-early.service` | 保命：异常重启落 TWRP | 失去"崩溃自动进恢复"的保险（见 §十） |
| `umi-return-recovery.service` | 配合上面的返回恢复逻辑 | 同上 |
| `boot-collect.service` | 每次开机采集诊断快照到 `/data/diag/` | 出问题没有现场日志 |
| `umi-put.service` | 8080 无鉴权 HTTP 文件服务 | **默认已不自启**，需要时手动 `start` |

**CPU 策略**（`cpupower`）：

```bash
cat /etc/default/cpupower          # GOVERNOR="performance"
systemctl restart cpupower
cat /sys/devices/system/cpu/cpufreq/policy*/scaling_governor
```

> `performance` 的价值是**消除爬频延迟**（突发负载更跟手），代价是空闲功耗上升；
> 持续满载吞吐与 `schedutil` **几乎没有差别**。想省电就改回 `schedutil`。

## 十、保命机制与"怎么重启"

这台机器有一套**故意设计**的保险：**异常重启会落进 TWRP 恢复模式**，避免刷坏了只能靠串口硬救。

因为 rootfs 直接住在 `userdata` 分区，所以有个路径映射必须记住：

```
Linux 里的   /data/xxx      =   TWRP 里的   /data/data/xxx
（Linux 的根 = TWRP 的 /data）
```

| 标志位（Linux 侧） | 作用 |
|---|---|
| `/data/AUTO_RECOVERY_OFF` | **存在** = 正常重启回 Linux；**不存在** = 每次开机都写 `misc` 让机器落 TWRP |
| `/data/HOLD` | 保命网的状态标志 |
| `/data/NO_RETURN` | 禁止自动返回（用于特殊调试） |

```bash
ls -l /data/                         # 看标志位
touch /data/AUTO_RECOVERY_OFF        # 让它正常重启到 Linux（安装 TWRP 环境后建议加上）
rm /data/AUTO_RECOVERY_OFF           # 重新"武装"保命网（重启就进 TWRP）
```

**已经从 TWRP 里了，想正常开机进 Linux**（清 BCB）：

```bash
dd if=/dev/zero of=/dev/block/by-name/misc bs=1 count=32 conv=notrunc
```

**重启 / 关机**：

```bash
reboot            # 尊重上面的标志位
poweroff          # 正常关机
# 物理按键：短按电源键 = 干净关机（不是唤醒屏幕）
```

## 十二、故障排查表

| 现象 | 先查什么 | 可能原因 / 处理 |
|---|---|---|
| **开机后 USB 网卡和串口都不出现** | 设备是否真的启动了（屏幕/电流） | 大概卡在引导：DTB 不合格（缺 `__symbols__`/锚点）→ 秒进 fastboot。重新刷回已知可用的 boot（`tools/restore-system-opensource.sh` 同目录的配套镜像） |
| **屏幕一直黑** | `systemctl status panel-off` | **正常现象**（面板已断电）。不是故障 |
| **`ssh` 连不上 `172.16.42.1`** | `ipconfig` 看网卡有没有 `172.16.42.2` | 手动给网卡配 `172.16.42.2/16`；或换串口进来排查 `systemctl status usb-gadget-umi` |
| **串口没输出** | 设备管理器有没有 COM 口；波特率是否 115200 | 换根**数据线**（很多线只供电不传数据）；确认没有别的程序占着串口 |
| **WiFi 起不来** | `lspci -nn \| grep 17cb`、`dmesg \| grep ath11k` | 没有 `01:00.0` 端点 → PCIe/PMU 上电失败；检查是否有电源域被你改坏（回滚 DTB） |
| **WiFi 连不上但 wlan0 在** | `wpa_cli -i wlan0 status` | 密码错（重跑 `wifi-connect.sh`）；`rfkill list` 看是否被 block；路由器 MAC 绑定 → 配 `10-wlan-mac.link` |
| **不充电了** | `cat /sys/class/power_supply/pm8150b-charger/charging_enabled` | 大概率是**充电区间控制正在正常工作**（已达上限停充）；若你停过服务，记得 `echo 1 > charging_enabled` |
| **`/dev/video*` 不存在** | `journalctl -u umi-venus-enable -n 50` | MMCX 电源域没起来或模块加载失败；重启该服务 |
| **`/dev/dri/renderD128` 不存在** | `dmesg \| grep -iE 'adreno\|msm'` | 开机 zap 报错是**无害的**，打开一次渲染节点会重试成功；若仍无 → 回滚 boot |
| **多路编码时 ffmpeg 崩溃** | 输入高度是否 720 这类非 32 对齐值 | 改成 736p/1088p（FFmpeg 7.x 上游 bug） |
| **GPU 满载后死机/花屏** | `dmesg \| grep -i 'gpu fault\|hangcheck'` | 频率超太高。把 `/etc/default/umi-gpu-maxfreq` 调回 `587000000` |
| **突然 kernel panic 后自动重启** | `/sys/fs/pstore/`（pstore 有转储） | 本项目已知的踩雷：读 `qfprom0/nvmem` 会 panic；其他则是**访问已断电外设 MMIO**。看转储定位 |

## 十三、⚠️ 三条硬红线

1. **不要碰基带相关分区**：`modemst1/2`、`fsg`、`fsc`、`persist`、`mdm1m9kefs*`。
   擦掉 → IMEI / 基带 / WiFi MAC 永久丢失。
2. **不要读 `/sys/bus/nvmem/devices/qfprom0/nvmem`**（efuse）→ 直接 kernel panic。
   同理**任何已断电外设的 MMIO 都不要碰**。
3. **不要动原厂 `dtbo` 分区**，必须保持原厂镜像。
